# Deploy na Vercel: client e server como Services do mesmo projeto

Em produção, o client (Vite) e o server (Express) sobem como dois Services de um projeto só na Vercel (`vercel.json` na raiz), com o Postgres no Neon. O navegador fala com uma origem só: `/api`, `/graphql` e `/health` vão para o server, e o resto para o client. Assim o cookie de sessão continua valendo para tudo, como no proxy do Vite. Descartamos a Railway (paga) e a Render (o server dorme quando ninguém usa) porque queríamos tudo num lugar, sem custo para começar.

O server na Vercel roda como Funções, e não num processo que fica ligado. Isso muda três coisas do ADR 0010. `app.ts` monta o app, e `index.ts` continua sendo o processo de sempre para rodar local e no Docker. Um Trabalho roda dentro de `waitUntil`, que mantém a Função viva até ele terminar, até o `maxDuration` de 5 minutos. Como não há boot para varrer os que morreram, `failStaleJobs` marca como falhos os que estão na fila ou rodando há mais de 10 minutos. Ele roda no Cron e antes de contar os Workflows em andamento (`requireRoom`). As Rotinas não têm relógio: um Cron Job da Vercel chama `/api/cron/routines` com o `CRON_SECRET`. No plano Hobby isso acontece uma vez por dia, então uma Rotina pode rodar até um dia depois da hora marcada.

Cancelar um Trabalho continua correto, porque o estado no banco manda. Mas, se o pedido de cancelamento cair numa Função diferente da que roda o Trabalho, o Modelo segue escrevendo até o fim e o texto é descartado. Quando isso pesar, ou quando os Trabalhos passarem de 5 minutos, o caminho segue o mesmo do ADR 0010: uma fila com um worker à parte (Vercel Queues ou Daemons).
