# WhatsApp pela Cloud API da Meta, só respondendo, com um teto mensal

Substitui o ADR 0014 na parte do Twilio. O resto dele continua valendo: a API oficial, um número só (o do Caishen), só as finanças do Usuário, e o WhatsApp como mais um canal da mesma Conversa, com o mesmo `replyInConversation`, os mesmos Limites do Plano e as mesmas Propostas (ADR 0013).

Falamos direto com a WhatsApp Cloud API da Meta, por REST e sem SDK, como com o Stripe (ADR 0011). O Twilio cobra uma taxa por mensagem por cima da Meta, e o requisito agora é custo zero. A Cloud API é grátis. As respostas a quem escreveu (mensagens de serviço, dentro da janela de 24 horas), inclusive com botões interativos, são grátis até 1.000 por mês por número. Os templates, mesmo os de utilidade, são pagos desde 01/10/2026. Por isso o Caishen **só responde, nunca inicia**: não há Avisos proativos pelo WhatsApp, e uma Proposta confirmada depois no app não manda nada. Não cadastramos forma de pagamento na Meta, então além do teto as mensagens simplesmente não saem, sem cobrança surpresa.

Contamos as mensagens enviadas no mês de São Paulo (`whatsapp_usage`), uma por parte de texto, já que uma resposta longa é quebrada em partes de até 4.096 caracteres. O teto é `WHATSAPP_MONTHLY_CAP` (padrão 1.000) para a conta inteira. A última vaga fica guardada para um "continue pelo app"; depois dela, nada sai até o mês virar. Por isso o prompt do canal pede respostas curtas. Um teto por Plano ou por Usuário fica para quando houver mais de um número de destino. O número de teste da Meta só manda para 5 números cadastrados.

O vínculo é por Usuário (`whatsapp_link`). Em Integrações, o Usuário gera um código de uso único que vale 15 minutos (`whatsapp_link_code`). O botão abre `wa.me` com o código no texto, e a primeira mensagem com ele liga aquele número ao Usuário. Guardamos o número exatamente como a Meta o manda (o `wa_id`), sem normalizar: no Brasil o `wa_id` pode vir sem o nono dígito, e como o vínculo é por código, nunca precisamos ler um telefone digitado. Na tela, o número aparece mascarado. A cada mensagem conferimos de novo que o Usuário ainda é Membro da Organização; se não for, o número conta como desconhecido. "SAIR" desfaz o vínculo.

Um número desconhecido sem código recebe as instruções uma vez só. Para isso guardamos um hash SHA-256 do número (`whatsapp_stranger`), nunca o número nem a mensagem. É o mínimo para não responder a cada mensagem e gastar o teto.

O webhook confere o `X-Hub-Signature-256`, um HMAC-SHA256 do corpo bruto com o App Secret, responde 200 na hora e processa depois (`waitUntil`, ADR 0012). A Meta reenvia entregas, às vezes ao mesmo tempo. Por isso as três operações sensíveis são uma instrução só no banco, nunca "lê e depois grava": o descarte de repetidas é um insert do `wamid` com `on conflict do nothing`, o uso do código é um update condicional, e o teto é um upsert que soma e devolve o total.

Cada Organização tem uma Conversa do canal WhatsApp (`conversation.channel`, com um índice único parcial), com o título "WhatsApp". Ela aparece também no Agente. É uma Conversa só para sempre: o Modelo já vê só as últimas 20 Mensagens. Cada Proposta nova sai como o texto de `describeProposal` mais os botões Confirmar e Cancelar, com o id da Proposta no botão. "Sim" ou "não" por texto decide a Proposta pendente mais recente dessa Conversa. A Proposta tem de ser da Organização do número que respondeu (`owned`). Por enquanto, só texto: áudio, imagem e documento recebem "por enquanto, só texto" (fases 2 e 3).

Sem as variáveis (`WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_NUMBER`), o webhook responde 404 e a Integração aparece indisponível. Descartamos as bibliotecas não oficiais (Baileys, whatsapp-web.js): violam os termos, o número pode ser banido, precisam de um processo sempre ligado que a Vercel não tem, e guardam a sessão do celular, que é uma credencial (ADR 0009).
