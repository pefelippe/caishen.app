# AGENTS.md

Guidance for AI coding agents working in this repo. Keep it terse.

## Read first

- **`CONTEXT.md`**: domain glossary (pt-BR terms plus their code names). Use its terms; its `_Avoid_` lists are binding.
- **`docs/adr/`**: decisions that look surprising without context. Do not "fix" them silently.

## Structure

Turborepo + pnpm (hoisted `node_modules`), mirroring `www/monorepo`.

- `apps/server`: Express 5 + Apollo Server (`/graphql`) + Better Auth (`/api/auth`) + Bot chat (`POST /api/chat/:conversationId`, server-sent events). Bots run in `src/services/bots`: the catalog (`catalog.ts`), what each Bot knows (`context.ts`), its prompt, the chat loop and the Job runner (`jobs.ts`, in-process, ADR 0010). They reach Models only through `src/services/models.ts` (`talk`, `listModels`, `defaultModel`, each for an Organization), over `@zapbots/ai` with the Organization's keys (`services/aiKeys.ts`, ADR 0022). The read tools' code is `services/bots/tools.ts`.
- `packages/ai` (`@zapbots/ai`, ADR 0021): the engine Bots talk to Models through, on the AI SDK: providers (OpenRouter, Anthropic, Google, OpenAI; a saved id `anthropic:…` goes straight to that provider, anything else is OpenRouter's), the catalog of direct Models, errors in pt-BR (`ModelError`) and the agent loop (`runAgent`: one call per round, the last without tools, no SDK retries). No database and no domain.
- `packages/bots/*`: one package per Bot, with its catalog entry and its pure logic. No I/O there; database and Model calls stay in `apps/server`.
  - `packages/bots/finance` (`@zapbots/finance`): Caishen, the finance Bot. Pure financial math (amortization, Implied Rate, Assessment) with tests; all financial logic lives here. Also its instructions (`prompt.ts`, `caishenInstructions`: sections, mistakes and examples; the server only adds the data) and the specs of its read tools (`tools.ts`).
- `packages/database`: Drizzle schema, migrations (`drizzle/`), lazy `db` client.
- `packages/auth`: Better Auth instance + `resolveViewer(headers)`.
- `packages/graphql`: SDL schema, client operations (`src/operations/*.graphql`), codegen output (`src/generated`, gitignored).
- `packages/ui` (`@zapbots/ui`): the design system. shadcn/ui components in `src/components` (`@zapbots/ui/components/button`), our own building blocks that know nothing of GraphQL, i18n or the router in `src/blocks` (`Field`/`PageHeading`, `Metric`, `CalcField`, `PageSkeleton`, `Section`/`SectionRow`, `Logo`/`Splash`, `AgentIcon`, the Model providers' marks (`provider-logos`: `OpenRouterLogo`, `AnthropicLogo`, `GeminiLogo`, `OpenAiLogo`), the services' marks on Integrações (`brand-logos`, from Simple Icons), `Kbd`, `BottomSheet` (a phone sheet that follows the finger down to close)), `cn` (`@zapbots/ui/lib/utils`), `useIsMobile` and the theme (`src/styles/globals.css`: tokens, `.dark`, `@theme`, base layer; it carries the `@source` that makes Tailwind read the package). Files inside it import each other by the package name. No build step, like the rest.
- `packages/client`: React + Vite + Apollo Client 4. Vite proxies `/api` and `/graphql` so every request shares one origin and one session cookie.
  - UI is shadcn/ui on Tailwind v4. Every control or surface (button, input, select, table, card, alert…) is a shadcn component from `@zapbots/ui`. Add missing ones with `pnpm dlx shadcn@latest add <name>` from `packages/ui`; a component that knows nothing of the app goes in `packages/ui/src/blocks`. Never use raw `<button>`/`<input>`/`<select>`/`<table>`.

Workspace packages have no build step: `main` points at `src/index.ts`; apps run with `tsx`. Production is one Vercel project with two Services, `client` and `server` (`vercel.json`, ADR 0012): `apps/server/src/app.ts` is the Express app, `index.ts` the long-lived process around it. The server's build runs `pnpm db:migrate` before codegen, so each deploy brings the production database up to the code (migrations must stay additive: a new column nullable or with a default).

## Conventions

- Code in English, UI in pt-BR.
- Commits are semantic (Conventional Commits: `feat(scope): summary`, `fix`, `refactor`, `docs`, `test`, `chore`), one subject each. Never add Claude (or any AI) as co-author: no `Co-Authored-By` trailer.
- Money is integer cents (`number`, `bigint` in Postgres); rates are monthly effective fractions. Money math uses `decimal.js` in `@zapbots/finance`, never `float` arithmetic (ADR 0004).
- Every query or mutation scopes by `viewer.organizationId`: build the filter with `owned(table, viewer, id?)` from `resolvers/guards.ts`, never by hand, and load a Holder through `findHolder`. The Organization is personal and has its own page; changing it takes `requireAdmin`. Finanças uses the `viewerHolder` (ADR 0007).
- Legal (ADR 0027): the Termos and the Política (`LegalPage`, the controller in `lib/legal.ts`) describe what the code does: a new kind of data, a new outside service or a new cookie changes them and `LEGAL_UPDATED`. Excluir conta (`deleteAccount`, `services/account.ts`) takes every Organization where the User is alone, ending its Stripe subscription first; a new table must hang off the Organization with `onDelete: cascade` (or off the user) so it goes too. The Caishen's prompt answers a person in crisis first (`CARE`: CVV 188, SAMU 192).
- Bots only read (ADR 0009): nothing written outside zapbots, no money moved. They reach outside tools only through Connections (OAuth), never with stored passwords. Give Models money already formatted.
- Chat Messages can carry Anexos (ADR 0017): the + in `ChatThread` (and on the Dashboard's ask line, which hands them to the chat panel through `startNew`), or pasting a file or screenshot, reads spreadsheets and text in the browser (`lib/attachments.ts`, `addAttachments`), scales photos down and sends PDFs whole, inline in the chat request (5 files, 3 MB of images and PDFs); `services/bots/attachments.ts` checks them and builds the Model's parts. Images need a Model that reads them (`readsImages`); PDFs go through OpenRouter's free `file-parser`, or as a native file part on a direct provider. Only names are kept (`message.attachments`).
- Models have two kinds of tools. Read tools (ADR 0021: `period_summary`, `list_expenses`, `simulate_prepayment`, `payoff_plan`, and `company_lookup`, ADR 0024) read the session's Holder only (`company_lookup` may also look up a CNPJ the person names: public registry data) and answer with money already formatted; Jobs get only these. In the chat, the other tools propose records: new ones, corrections or deletions of saved ones (ADR 0013, `services/bots/proposals.ts`): a tool call stores a PENDING Proposal; only `confirmProposal` writes, through the services in `services/records.ts` (`updateRecord` for corrections, `deleteRecord` for deletions). Values arrive as people type them and are read by `inputFor` (`services/recordForms.ts`), the same for the Model, the Proposal card (`editProposal`) and the Editar dialog of saved records (`recordFields`/`updateRecord`, `EditRecordDialog`); the Holder comes from the session. New write paths go in `records.ts`, shared by resolver and Proposal. A deletion, too, happens only on the User's confirmation.
- A Bot is an entry in `CATALOG` (`services/bots/catalog.ts`) with its name and personality fixed in its package; the `bot` table only stores which Organization has it and its Model (ADR 0010).
- A Job runs in the server process; `createJob` starts it and the client polls `job`. On boot, unfinished Jobs are marked failed; on Vercel, `failStaleJobs` does it to Jobs past their function's time limit (ADR 0012). Hand Jobs over only through `handOverJob` (`services/bots/jobs.ts`); requests from Users also pass `requireRoom` (at most 3 Jobs in progress per Organization).
- A Routine hands the same Job over every week or month; `startRoutineClock` checks once a minute in the server process (ADR 0010); on Vercel a daily Cron Job calls `/api/cron/routines` instead (ADR 0012).
- A Connection is an entry in `services/connections.ts` (kind, category, status) plus its copy on the Integrações page.
- Changing the GraphQL schema or operations: run `pnpm codegen`.
- Changing the Drizzle schema: run `pnpm db:generate`, then `pnpm db:migrate`.
- Changing scoring rules in `assessment.ts`: bump `ASSESSMENT_MODEL_VERSION`. The scale (0–1000, SPC bands, 4.966 Stages) is fixed by ADR 0005.

## Commands

- `pnpm tui` (`scripts/tui.mts`): `.env`, Docker, install, Postgres, migrations and codegen, then server and client in one screen (`--skip-install`). See `docs/local-development.md`.
- `pnpm infra:up`, then `pnpm db:migrate`, then `pnpm dev`: Postgres in Docker, apps on the host.
- `docker compose up --build`: everything in containers.
- Bots need an AI key pasted on Integrações (ADR 0022: per Organization, admins only, sealed in `ai_key` with AES-256-GCM under `BETTER_AUTH_SECRET`; only `last4` leaves the server). The one exception: `OPENROUTER_API_KEY` in `.env`, if set, serves OpenRouter's free Models (only those) to Organizations without an OpenRouter key of their own (`keysOf` in `services/models.ts`). Without any key the Bot panels point to Integrações. Server tests get an OpenRouter key from `createViewer` (`aiKey: false` leaves it out).
- Server tests (`apps/server/src/__tests__`) use a real Postgres database, `zapbots_test`, created and migrated on demand, so they need `pnpm infra:up`. External APIs are faked with MSW (`apps/server/test/msw`); our own code is not mocked. One test file per feature.
- `pnpm test:unit` · `pnpm lint:tsc` · `pnpm lint`
